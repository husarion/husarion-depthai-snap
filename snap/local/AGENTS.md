# husarion-depthai snap — operator guide

On-device usage reference for the **installed** `husarion-depthai` snap, written for AI assistants and operators working on the robot. It is regenerated from the snap on every install/refresh — do not edit it (changes are overwritten).

## What this is

ROS 2 driver for Luxonis OAK-x depth cameras on Husarion robots. Publishes RGB (and, when enabled, depth + pointcloud) under `<namespace>/<name>/...` — default node name `oak`, so e.g. `/rosbot/oak/rgb/image_raw`.

## First run

```bash
sudo /var/snap/husarion-depthai/common/post_install.sh       # interfaces + refresh hold
sudo snap set husarion-depthai driver.model=<model>   # e.g. OAK-D-PRO
sudo husarion-depthai.start
```

## Configuration — two ways

1. **Husarion cockpit (recommended in a cockpit install).** The ROS network (RMW, `ROS_DOMAIN_ID`, namespace) is set on the chain **owner** — the `rosbot` snap or the cockpit host — from the WebUI **Manage** tab, and propagates here automatically. Do **not** hand-set `ros.*` here in a cockpit install. The operator camera/streaming UI ingests this snap's image topic.

2. **Direct / standalone:** `sudo snap set husarion-depthai <key>=<value>`:

   - `driver.name` — node name + topic prefix.
   - `driver.model` — REQUIRED before start; e.g. `OAK-D`, `OAK-D-PRO`, `OAK-1` (hardware is auto-detected; this is validation/cockpit metadata).
   - `driver.camera-params` — almost never needed; there is one bundled preset (`default`) and everything below overrides it. Only set this to point at a hand-authored custom preset (see "Camera pipeline config" below).
   - `driver.depth` (default `false`) — adds metric depth + an on-chip H.264 disparity preview; rejected on OAK-1/OAK-1-LITE.
   - `driver.pointcloud` (default `false`) — setting this `true` automatically sets `driver.depth=true` too (a pointcloud needs a depth topic to draw from).
   - `driver.resolution` (default `720P`; `720P`/`1080P`/`4K`), `driver.fps` (default `30`; 1-60).
   - `driver.imu`, `driver.ir` (both default `false`) — capability-gated per model. `ir` toggles the IR laser dot projector AND floodlight together (one upstream switch).
   - `driver.ip` (no default, unset = USB) — PoE target address.
   - `driver.rectify-rgb`, `driver.startup-delay`.
   - `ros.namespace`, `ros.domain-id`, `ros.transport`.

   All of the above are rejected at `snap set` time with a clear reason if the camera model doesn't support them — never a silent no-op. Note: the concrete defaults still apply even against a custom `driver.camera-params` file (except `ip`, which stays unset) — a hand-authored RGBD preset still needs `driver.depth=true` set explicitly, or the `false` default downgrades it to RGB at launch.

## ROS network / RMW config locations

- Effective ROS env: `/var/snap/husarion-depthai/common/ros.env`.
- RMW profile files: `/var/snap/husarion-depthai/common/rmw/`, and the chain config under `/var/snap/husarion-depthai/common/husarion-agent/config/`.
- `ros.transport` selects FastDDS / CycloneDDS profiles only. **Zenoh reaches this snap through the agent chain** from the owner, not via `ros.transport`.

## Camera pipeline config locations (camera-params)

The depthai_ros_driver pipeline YAML lives in **`/var/snap/husarion-depthai/current/`** (per-revision, `$SNAP_DATA`). `driver.camera-params` almost never needs touching directly:

- `camera-params-autogenerated.yaml` (the default) — compiled fresh from `driver.depth`/`resolution`/`fps`/`imu`/`ir`/`ip` on every `snap set` by `generate_camera_params.sh`. Always the custom `husarion_depthai_pipeline` dual plugin (see below): raw RGB (autonomy) **and** on-chip H.264 (telepresence) from one camera at once, on every OAK-x including single-sensor OAK-1/OAK-1-LITE. Never hand-edit this file — it's overwritten on the next `snap set`.
- Anything else `driver.camera-params` points to is a hand-authored file — fully hands-off, `depth`/`resolution`/`fps`/`imu`/`ir`/`ip` have no effect on it. Copy `camera-params-autogenerated.yaml` to a new name to start one.
- `driver.ffmpeg-params` is still here — but scoped ONLY to `.../oak/rgb/image_rect` (the rectified stream, `driver.rectify-rgb=true`). On-chip H.264 (always on, see below) covers streaming for the RAW stream at near-zero CPU, but the on-chip encoder taps the raw frame — there's no hardware path for the *rectified* one, so this is a genuine host-CPU software encode when actually subscribed. See CLAUDE.md "The on-chip FFMPEGPacket is NOT the real ffmpeg_image_transport" for the full distinction.

### The custom dual-output pipeline plugin (always on)

The base preset publishes **raw `.../oak/rgb/image_raw` AND on-chip H.264 `.../oak/rgb/image_raw/ffmpeg` simultaneously** from one camera — autonomy (raw) + telepresence (chip H.264) at the same time. This used to be an opt-in preset family (`rgb-raw-*`); it's now unconditional (2026-08), since it strictly dominates the stock driver's exclusive raw-XOR-chip-H.264 path (see CLAUDE.md "Why the stock OAK chip H.264 encoder path is legacy now"). The topic suffix is `/ffmpeg` (renamed 2026-08 from `/compressed`, which by ROS convention means JPEG/PNG via `compressed_image_transport`, not H.264) — the message type is still `ffmpeg_image_transport_msgs/FFMPEGPacket`.

- **CUSTOM pluginlib plugin, not stock depthai, NOT a fork:** `husarion_depthai_pipeline` (classes `husarion_depthai::pipeline_gen::RGBDual` / `RGBDDual`), an external ament package built into this snap (durable source: the snap repo `ros/husarion_depthai_pipeline/`), registered via pluginlib so the stock `depthai_ros_driver` **autoloads it on demand** via `camera.i_pipeline_type`. `driver.depth` toggles between the two (`RGBDual` ↔ `RGBDDual`), compiled into `camera-params-autogenerated.yaml` by `generate_camera_params.sh`. **If the snap is rebuilt/refreshed WITHOUT the `husarion_depthai_pipeline` colcon-package in the `husarion-depthai` part of snapcraft, this fails to load.**
- **Under the hood (RGB leg):** taps one `ColorCamera.video` NV12 output to both a raw XLinkOut (→ `image_raw`) and the OAK hardware VideoEncoder (→ `image_raw/ffmpeg`). One dai output fanned to two consumers. No host encode, no `/dev/dri`, no new snap interface.
- **Verified live on an OAK-1 (USB3 SUPER, 2026-06-22):** raw 1280×720 + on-chip H.264 both at **30 fps**, daemon **~12.7% CPU** — that 12.7% is the host **NV12→bgr8** conversion for the raw topic (the encode is on-chip ≈free); contrast the stock raw-then-host-reencode path at ~98% of a core (transport-bound).
- **The FFMPEGPacket `encoding` token is the truthful `h264`** (the plugin sets it), unlike the stock low-bandwidth path's stale `libx264` label.
- **With `driver.depth=true` (`RGBDDual`):** adds depth 16UC1 raw (`…/stereo/image_raw`, metric, for autonomy) + a disparity grayscale-H.264 view (`…/stereo/image_raw/ffmpeg`, a lossy 2D depth *preview*, telepresence) + a lazy **software** PNG depth compressor (`…/stereo/image_raw/compressedDepth`, zero-cost unless subscribed — added 2026-08 via `enable_pub_plugins`). Needs a stereo-capable OAK (`configure` rejects `depth=true` on OAK-1/OAK-1-LITE). The on-chip encoder needs **8-bit** input, so this path forces `stereo.i_subpixel=false` automatically (subpixel → 16-bit disparity → the VideoEncoder rejects it; the metric depth raw and the compressedDepth PNG both stay full 16-bit precision regardless).
- **Suppresses the raw stream's unwanted image_transport republishers** (`oak.rgb.image_raw.enable_pub_plugins: ['image_transport/raw']`; `stereo.image_raw.enable_pub_plugins: ['image_transport/raw', 'image_transport/compressedDepth']` when depth is on). Without the RGB one, the raw publisher's lazy CompressedImage republisher would claim `.../image_raw/compressed` — a different, JPEG-flavored topic that would just confuse a consumer expecting either raw or the on-chip `/ffmpeg`, not an actual name collision anymore post-rename. The stereo allowlist specifically excludes `compressed`/`theora` (8-bit-only transports that mishandle 16-bit depth) while allowing `compressedDepth` (PNG, depth-aware).
- **Cockpit consumption:** the camera node needs to key off `.../ffmpeg` now (was `.../compressed`) — a cockpit-side config change, not a snap-side one; not verified from this repo.

> **Two gotchas when verifying chip vs host encode** (both bit a reviewer in 2026-06):
>
> - The `FFMPEGPacket.encoding` token reads **`libx264`** on the legacy stock low-bandwidth path (`i_low_bandwidth_ffmpeg_encoder` is declared but never read back; see CLAUDE.md "Pitfalls") — do **not** read it as "host re-encode". Use **daemon CPU** as the signal: ~few % = chip, ~100%+ = host libx264.
> - `ros2 topic list` may still show `.../oak/rgb/image_raw` even after a change that should drop it — a *subscriber* (e.g. the cockpit camera node holding its previous source) keeps the topic name alive. Check `ros2 topic info` **Publisher count**, not mere presence.

### Rectified RGB (`image_rect`) — real `ffmpeg_image_transport`, host CPU

`image_proc::RectifyNode` (loaded when `driver.rectify-rgb=true`, the default) publishes `.../oak/rgb/image_rect`. Unlike the raw stream, this has **no hardware encode path at all** — the on-chip VideoEncoder taps `ColorCamera.video` before rectification. So this snap still stages the REAL `ros-{distro}-ffmpeg-image-transport` plugin + `ffmpeg` CLI, configured by `driver.ffmpeg-params` (`ffmpeg-params-default.yaml`, `image_rect.ffmpeg.*` — libx264, 2 Mbps, `preset:ultrafast,tune:zerolatency`), just for this one topic. It's a genuine `image_transport::PublisherPlugin` this time (not a plain `rclcpp::Publisher` like the on-chip legs) — lazy, so ~127%-of-a-core host CPU only while something is actually subscribed to `.../image_rect/ffmpeg`.

- **`enable_pub_plugins` fix (2026-08):** `RectifyNode` never had this set, so image_transport defaulted to loading **every installed plugin** — including `compressedDepth` (16-bit depth PNG), which is nonsense for 8-bit RGB. `ffmpeg-params-default.yaml` now sets `image_rect.enable_pub_plugins: ['image_transport/raw', 'image_transport/compressed', 'image_transport/zstd', 'image_transport/ffmpeg']` — explicit allowlist. `compressedDepth` excluded as a correctness fix; `theora` excluded by policy — no image published by this snap uses it.
- **Parameter prefix is `image_rect.*`, not `<name>.rgb.image_rect.*`** — ffmpeg_image_transport derives it from the publisher's own advertised (pre-remap) topic name, and `RectifyNode` advertises plain `image_rect`.

## Chaining (how it gets its network config)

Embeds `husarion-agent` as a chain **follower (leaf)**. Installed next to a `rosbot` snap (or a cockpit host) it auto-joins over the `agent-chain` content interface and inherits the owner's network config — nothing to configure. Set the network on the **owner**; it cascades here.

**Custom RMW profiles** are added on the **owner** (the rosbot snap, no cockpit needed): drop the XML in rosbot's `husarion-agent/config/rmw/<impl>/` and `snap set rosbot ros.transport=…` — the file and selection propagate here in ~0.5 s. Don't add a profile or set `ros.transport` here; the owner reconciles a local change away.

## Apps

`husarion-depthai.start` · `husarion-depthai.stop` · `husarion-depthai.restart`.

## Gotchas

- Big frames (1280x720 RGB ≈ 2.7 MB) fragment over UDP; a busy subscriber needs a large DDS receive buffer. A Husarion cockpit install raises the host `net.core.rmem_max` for this — on a bare standalone host, raise it yourself if a subscriber drops frames.
- Depth is off unless `driver.depth=true` (rejected on OAK-1/OAK-1-LITE).
- `post_install.sh` **holds automatic snap refreshes** for this snap (an unattended store refresh would restart the driver and could move the robot off its validated revision — and the dual-output pipeline NEEDS the snap's own plugin part, so a surprise revision swap is extra risky here). Update deliberately with `sudo snap refresh husarion-depthai`; `sudo snap refresh --unhold husarion-depthai` restores auto-refresh.
