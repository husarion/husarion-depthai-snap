## 1. Overview

`husarion-depthai` is a **strict-confinement snap** containing a complete ROS 2 node with the Luxonis OAK-x camera driver (`depthai-ros`), wrapped in a configuration layer typical of Husarion snaps (`driver.*` + `ros.*` via `snap set`, DDS XML, ros.env, command-chain).

## 4. Domain models

### Snap parameters (external contract)

```
husarion-depthai (snap)
├── driver.*                              # DepthAI-specific; handled by snap/hooks/configure
│   ├── name              = oak           # node name; regex ^[a-z_-]{1,10}$
│   ├── model             = (unset)       # REQUIRED before start: OAK-D | OAK-D-LITE | OAK-1 | OAK-1-LITE | OAK-D-PRO | OAK-D-PRO-W
│   │                                       # snap-side validation only; depthai driver autodetects hardware
│   ├── camera-params     = autogenerated # name of camera-params-<NAME>.yaml in $SNAP_DATA
│   │                                       # "autogenerated" = compiled by generate_camera_params.sh from the keys below,
│   │                                       # on every configure run. Anything else = a hand-authored file, fully hands-off.
│   ├── startup-delay     = 30            # seconds 0-120 (allow-unset); workaround for USB cold-start race after reboot
│   ├── depth             = false         # RGBDual↔RGBDDual at launch. Rejected if true on OAK-1 / OAK-1-LITE.
│   ├── pointcloud        = false         # load PointCloudXyzrgbNode + force RGB/stereo sync; true CASCADES depth=true
│   ├── resolution        = 720P          # enum 720P|1080P|4K; overrides rgb.i_resolution
│   ├── fps               = 30            # number 1-60; overrides rgb.i_fps + H.264 keyframe cadence
│   ├── imu               = false         # rejected if true on a model with no IMU
│   ├── ir                = false         # IR laser dot + floodlight together; rejected if true unless OAK-D-PRO/OAK-D-PRO-W
│   ├── ip                = (unset)       # allow-unset IPv4; PoE target address — the one key with no default
│   └── rectify-rgb       = true          # bool; load image_proc::RectifyNode (forced off for raw-less presets)
│
└── ros.*                                 # shared; handled by configure_hook_ros.sh from snap-common
    ├── domain-id         = 0             # 0..232
    ├── localhost-only    = ''            # 0|1; ROS_LOCALHOST_ONLY; allow-unset
    ├── transport         = udp           # udp/shm/udp-lo, fastdds/<X>, cyclonedds/<X>, rmw_fastrtps_cpp, rmw_cyclonedds_cpp
    ├── namespace         = ''            # regex ^[0-9a-z_-]{1,20}$ (allow-unset)
    ├── automatic-discovery-range = ''    # subnet|localhost|off|system_default; allow-unset
    └── static-peers      = ''            # IPv4/IPv6/hostname; ; separated (jazzy only, allow-unset)
```

### Key file naming conventions

- `camera-params-<NAME>.yaml` — `depthai_ros_driver::Camera` parameters (sections `camera`, `imu`, `rgb`, `stereo`, `diagnostic_updater`). `NAME=autogenerated` is reserved (generated, never hand-edited); any other `NAME` is a custom, hands-off file.
- `rmw/<impl>/<NAME>.xml` — FastDDS profile (`xmlns="http://www.eprosima.com/XMLSchemas/fastRTPS_Profiles"`) or CycloneDDS (`xmlns="https://cdds.io/config"`). Type detected by `check_xml_profile_type` in `utils.sh`.

### ROS topics published (RGBD dual pipeline, `driver.depth=true`)

```
/<ns>/<name>/rgb/image_raw                  # sensor_msgs/Image (BGR8) — raw, autonomy
/<ns>/<name>/rgb/image_raw/ffmpeg           # ffmpeg_image_transport_msgs/FFMPEGPacket — ON-CHIP H.264 (~0 host CPU)
/<ns>/<name>/rgb/camera_info                # sensor_msgs/CameraInfo
/<ns>/<name>/rgb/image_rect                 # image_proc::RectifyNode — only if rectify_rgb=true
/<ns>/<name>/rgb/image_rect/ffmpeg          # REAL ffmpeg_image_transport plugin (host CPU — no hardware path for rectified)
/<ns>/<name>/rgb/image_rect/{compressed,zstd}  # other image_transport lazy republishers (still enabled; compressedDepth AND theora excluded — see enable_pub_plugins)
/<ns>/<name>/stereo/image_raw                    # depth 16UC1, metric, autonomy
/<ns>/<name>/stereo/image_raw/ffmpeg             # disparity grayscale H.264 — a lossy 2D depth *view*, telepresence (not metric)
/<ns>/<name>/stereo/image_raw/compressedDepth    # lazy SOFTWARE PNG depth compression (image_transport, on subscription only)
/<ns>/<name>/points                              # PointCloud2 (from PointCloudXyzrgbNode, if driver.pointcloud=true)
```

`husarion_depthai_pipeline` (the custom plugin, `ros/`) is unconditional — `camera-params-autogenerated.yaml` always sets `camera.i_pipeline_type` to `husarion_depthai::pipeline_gen::RGBDual` (RGB only) or `RGBDDual` (`driver.depth=true`), never a stock `RGB`/`RGBD` type. `generate_camera_params.sh` sets `oak.rgb.image_raw.enable_pub_plugins: ['image_transport/raw']` (and, when depth is on, `stereo.image_raw.enable_pub_plugins: ['image_transport/raw', 'image_transport/compressedDepth']`) so the raw stream's own lazy transport republishers don't collide with the on-chip FFMPEGPacket on `…/ffmpeg`, while still allowing the semantically-correct lazy software depth compressor. See README.md / snap/local/AGENTS.md for details + the depth `i_subpixel=false` constraint. A hand-authored custom `camera-params` file can still use a plain stock `RGB`/`RGBD` type if you want — those topics stay as documented above without the extra `/ffmpeg` legs.

## 7. Architectural decisions

### D1. Snap manifest generated from Jinja

**Why**: originally covered two ROS distros (humble/jazzy) with different `base:`/extension from one template. Humble support was dropped 2026-08 (EOL) — jazzy is the only target for now, with a distant-future `lyrical` distro a plausible next one. Kept the template (rather than hand-writing `snap/snapcraft.yaml`) so that future distro addition is a one-line `ROS_DISTROS` change, not a second near-duplicate manifest.

**Consequence**: `snap/snapcraft.yaml` is an artifact (gitignored), tooling has to remember to render — `justfile` and CI do that.

### D2. Extracting shared parts to `husarion-snap-common`

**Why**: identical hooks, validators, DDS XML, start/stop wrappers exist in many Husarion snaps (rosbot, webui, depthai…). Hosting them in a library shares the maintenance cost.

**Consequence**: cross-snap changes go through a PR to common + a pin bump in each consuming repo. Don't patch local copies.

### D3. `depthai-ros` from apt (not from source)

**Why**: a `colcon` build from `luxonis/depthai-ros` was slow and brittle (commit c986807 "install snap from apt packages"). apt is deterministic and 10× faster.

**Consequence**: the snap version's upstream part comes from the apt Candidate (see D3b). Upstream bug → wait for a package release. No way to use a commit-level pin.

### D3b. Snap version = `<upstream depthai-ros release>-<build date>`

E.g. `2.12.2-20260810`. Set in the `husarion-depthai` part's `override-stage`: the apt Candidate `2.12.2-1noble.20260616.073324` is cut at the Debian revision (`sed -E 's/-[0-9].*$//'`), then the injected build date is appended. A Candidate that doesn't start with a digit (`(none)` — package missing) degrades to `unknown-<date>`.

**Why**: the buildfarm tail is noise, and it shifts between the two arch runners when their apt caches differ — the same release would ship as two different versions. The date replaces it with one value per CI run, and it keeps two snap releases built off the same upstream package distinguishable (this repo's own content — presets, hooks, the `husarion_depthai_pipeline` plugin — moves without depthai-ros moving).

`build_date` comes from `render_template.py`: `BUILD_DATE` env if set, otherwise today's UTC date. `publish.yaml` computes it **once** in the `build-date` job and hands it to both matrix arches. `build.yaml` (PR, amd64-only) uses the local default. Same scheme in `rosbot-snap` and `husarion-rplidar-snap`, which take the upstream part from `git describe --tags` instead.

### D4. Startup-delay via uptime check

**Why**: `depthai_ros_driver::Camera` has a startup race after a fresh boot — the USB camera isn't ready yet and the driver crashes. Workaround: delay the start, but **only when we started shortly after system boot** (`/proc/uptime < STARTUP_DELAY + 60s`). In other cases (manual restart, refresh, crash recovery) we go without a delay.

**Earlier implementation** (up to `ecf72d9`, 2025-11-27): a flag file in `$SNAP_DATA/.startup-delay-done` + `exit 0` + `restart-condition: always` — the first iteration slept, the second (after a systemd restart) ran `ros2 launch`. It worked for the golden path, but: (a) risk of an infinite `sleep → launch fail → restart → sleep → …` loop, (b) the flag was deleted in iter 2, so every snap restart also paid the delay, (c) hard-to-follow logic with three coupled components.

**Current solution** ([snap/local/launcher.sh:63-71](snap/local/launcher.sh#L63)) is a clean branch on `int(/proc/uptime)`. Deterministic, requires only `/proc` (available under strict confinement without any plug). `restart-condition: always` stays on the daemon as general post-crash resilience, independent of the workaround.

**Status**: heuristic workaround. To be re-validated on every `ros-{distro}-depthai-ros` bump (procedure in [CLAUDE.md → "Before bumping apt dependencies"](CLAUDE.md)).

**Resolved**: the earlier `ros2 daemon stop && sleep 1` before `ros2 launch` (from commit 8f874b "test") has since been removed — `launcher.sh` now calls `ros2 launch` directly after the optional startup-delay sleep.

### D5. Two apps (`daemon` + foreground `husarion-depthai`)

**Why**: 99% of production cases = service. Foreground needed for debug and interactive sessions.

**Consequence**: both use the same `launcher.sh`. Foreground requires the daemon to be stopped — enforced by `check_daemon_running.sh` in the command-chain.

### D6. Strict confinement + shared-memory slot/plug within the same snap

**Why**: ROS 2 with FastDDS in SHM mode needs access to `/dev/shm`. Strict confinement blocks foreign SHM by default. The snap declares its *own* shared-memory slot and connects to it (auto-connect after `post_install.sh`).

**Consequence**: declaring a `shared-memory` slot needs a store snap-declaration (we have one, `allow-installation` for `shm-slot`). Local `review-tools` doesn't see it and always FAILs on `shm-slot` — see [CLAUDE.md → "Local `review-tools` always FAILs on `shm-slot`"](CLAUDE.md).

### D7. No `execstack` fixup for `libamdhip64.so*` (part dropped 2026-08)

**Why**: the `fix-execstack` part (2024-08 … 2026-08) was a no-op that solved a non-problem. Published revisions ship the library with `PT_GNU_STACK = RWE` regardless, nothing in the snap loads it (sole `DT_NEEDED` dependent: a UCX perftest plugin), and `review-tools` whitelists `libamdhip64.so.5.*` for the accidental ROCm execstack. Details + the verification commands: [CLAUDE.md → "`libamdhip64.so*` execstack"](CLAUDE.md).

**Consequence**: no apt `execstack` build-dependency. Don't re-add the part on a depthai-ros bump; check whether the lib is actually *loaded* first.

### D8. Pointcloud controlled via `driver.*`, not via the params YAML

**Why**:

- `pointcloud` is a "launch topology" decision (whether to load `PointCloudXyzrgbNode`), not a driver parameter per se — it can't be baked into `camera-params-autogenerated.yaml` the way `depth`/`resolution`/etc. can, since it's about which composable node the launch file loads, not a `depthai_ros_driver` param value.
- **Do NOT** inject `pipeline_gen.i_enable_sync=True`/`rgb.i_synced`/`stereo.i_synced` here, even though that's what upstream `camera.launch.py` does on `pointcloud.enable=true` — a prior version of this launch file did exactly that and it crashes the daemon: `PipelineGenerator::createPipeline` (v2.12.2-jazzy) unconditionally builds a `dai_nodes::Sync` node when `i_enable_sync=true`, then links in each active pipeline node's `getPublishers()`. `RGBDual`/`DepthDual` always return `{}` there (deliberate — this dual-output pipeline's raw/encoder taps are inherently unsynced), so the Sync node gets zero inputs and the device pipeline build throws `Sync(17) - No inputs`, killing the container. Confirmed live 2026-08 (crash-loop on every `pointcloud=true`) and fixed by removing the override entirely — `PointCloudXyzrgbNode`'s own ROS-side `message_filters::ApproximateTime` sync is what actually matches RGB/depth frames, no device Sync node needed.

**Consequence**: `camera-params-*.yaml` describe ONLY driver parameters (sensors, pipeline, IMU) — `pointcloud` is the one exception left as a launch-time decision in `depthai.launch.py` (just the extra composable node, no parameter overrides); everything else (`depth`/`resolution`/`fps`/`imu`/`ir`/`ip`) is compiled into the file itself by `generate_camera_params.sh` instead (see D9). `pointcloud` also sits at the top of the `rectify-rgb`/`depth`/`pointcloud` dependency chain enforced in `configure` (2026-08) — cascades both ways (on upward, off downward); full rationale in [CLAUDE.md](CLAUDE.md).

### D9. `camera-params` compiled at configure-time (autogenerated), not overridden at launch-time

**Why**: an earlier design (superseded 2026-08) had `depthai.launch.py` parse the resolved `params_file` at launch and merge override dicts for `depth`/`resolution`/`fps`/`imu`/`ir`/`ip`. Two problems: (1) it only ever covered the specific fields it was written for — `depthai_ros_driver` has many more (`align_depth`, `lr_check`, `i_nn_type`, ...) that stayed inaccessible without a custom file anyway; (2) it ALSO clobbered a hand-authored custom file's own values for those same fields (e.g. a custom `i_pipeline_type: RGBD` file still got forced back to RGB by the `depth=false` default) unless the operator remembered to mirror every field on top of their own file — a real footgun.

**Consequence**:

- `driver.camera-params` has exactly two modes: `autogenerated` (default) — [generate_camera_params.sh](../snap/local/generate_camera_params.sh), run by `configure` on every `snap set`, compiles `depth`/`resolution`/`fps`/`imu`/`ir`/`ip` into `camera-params-autogenerated.yaml` from scratch (always the custom-plugin `RGBDual`/`RGBDDual`, never a stock type) — or anything else, a hand-authored file that's **fully hands-off**: generation skips entirely, those six keys have zero effect, logged not silent.
- `driver.depth` defaults to `false` (2026-08). Turning it on sets `i_pipeline_type=RGBDDual`, forces `stereo.i_subpixel=false`, and adds the stereo republisher suppression — see CLAUDE.md "depth/resolution/fps/imu/ir".
- Rejected at `snap set` time (`configure` hook, before `generate_camera_params.sh` even runs) if `driver.model` has no stereo pair (`OAK-1` / `OAK-1-LITE`). `driver.pointcloud=true` cascades `driver.depth=true` (same capability gate) — see CLAUDE.md.
- `depthai.launch.py` is back to loading `params_file` verbatim — no YAML parsing at launch, no pipeline-family state machine, no `yaml` import.

### D10. Custom `depthai.launch.py` instead of delegating to upstream `camera.launch.py`

**Why we keep our own launch**:

- Composable node naming (`<name>_rectify_color_node` instead of upstream `rectify_color_node`) — preparation for multicam.
- No dependency on `urdf_launch.py` from `depthai_descriptions` — Husarion has its own robot URDF.

**Coverage versus upstream `camera.launch.py` jazzy 2.12.2**:

| Upstream feature | Status here |
| -- | -- |
| `ParameterFile(LaunchConfiguration("params_file"), allow_substs=True)` | ✅ |
| `IfCondition(rectify_rgb)` + RectifyNode | ✅ (per-camera name) |
| `IfCondition(pointcloud.enable)` + PointCloudXyzrgbNode | ✅ as `pointcloud` |
| Sync overrides (`pipeline_gen.i_enable_sync`, `rgb.i_synced`, `stereo.i_synced`) | ❌ deliberately NOT injected — crashes the custom dual pipeline (see D8) |
| `tf_params` from `publish_tf_from_calibration` + `override_cam_model` | ❌ removed as dead (Husarion uses own robot URDF; would conflict) |
| `target_container` namespace-aware | ✅ (with leading `/`) |
| Default `camera_model` | driver.model has NO default — required at start (legacy driver.camera-model is migrated) |
| Default `rectify_rgb="true"` | ✅ aligned |
| `Node(rviz2)` + `use_rviz` | ❌ not needed (we have `image_view_launcher.sh`) |
| `IncludeLaunchDescription(urdf_launch.py)` | ❌ deliberately omitted |
| `rs_compat` (RealSense compat) + `enable_color/depth/infra*`, `*_profile` args | ❌ deliberately omitted |
| `setup_launch_prefix` (gdb/valgrind/perf) | ❌ omitted (snap strict confinement limits debug tools anyway) |

**Future decision**: could switch to `IncludeLaunchDescription(camera.launch.py)` mapping our `driver.*` to upstream args, but we'd lose control over node naming. Low priority — current coverage is complete.

### D11. Snap Store channels: branch → edge, tag → candidate

**Why**: `main` has working code, but not necessarily production-tested → `edge`. Git tags = intentional release → `candidate` (manually promoted to stable from there).

## 9. Known limitations / technical debt

1. **"startup-delay" workaround** — heuristic, not a root-cause fix. The uptime-based mechanism is simple and deterministic, but assumes that `int(/proc/uptime) < STARTUP_DELAY + 60s` is a good proxy for "fresh boot". Sanity-check procedure on a depthai-ros bump: [CLAUDE.md → "Before bumping apt dependencies"](CLAUDE.md).

2. ~~`${SNAP_COMMON}` is not synced on refresh~~ — **resolved**: yaml presets live in `${SNAP_DATA}` and are refreshed by the `post-refresh` hook. User customs survive (snapd copies `$SNAP_DATA` per revision). Legacy customs from `$SNAP_COMMON` are migrated once.

3. **`ros2-{distro}-ros-base` extension requires an experimental flag** — `SNAPCRAFT_ENABLE_EXPERIMENTAL_EXTENSIONS=1`. If that flag is removed/renamed, the build breaks.

4. ~~`fix-execstack` requires apt `execstack`~~ — **resolved**: the part was dropped (see D7), so no `execstack` build-dependency. Residual: `libamdhip64-5` (~24 MB) still stages as an unused transitive dep on amd64; prunable via `prime: -usr/lib/x86_64-linux-gnu/libamdhip64.so*` if the snap size ever matters.

5. ~~`humble` track~~ — **dropped 2026-08**: ROS 2 Humble reached EOL, `jazzy` is now the only supported distro. `render_template.py`'s `ROS_DISTROS` tuple and the CI matrix are both jazzy-only; re-adding a distro (e.g. a future `lyrical`) is a one-line change in each.

6. **Snap version tracks the apt Candidate** — a stale apt cache on a GH Actions runner still changes the upstream part of the version; only the buildfarm timestamp jitter is gone (see D3b).

7. **No unit/integration tests** — the only validation is "snap install --dangerous" in CI. Runtime regressions (e.g. a change in `launcher.sh`) are caught only by manual launch on the target platform.

8. **Snap size ~543 MB** — large surface, long `snap download`/`refresh`. Most of it is ROS 2 base + depthai-ros + ffmpeg (kept — see D9/D8 for why `ffmpeg`/`ros-{distro}-ffmpeg-image-transport` are staged despite the on-chip H.264 path: `image_rect` has no hardware encode alternative). Optimizing via `stage-snaps` instead of `stage-packages` would be possible but unverified.
